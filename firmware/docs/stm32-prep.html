01 / INSTALLWhat to put on the machine now

All of this installs and runs with no board attached. Do it now so day one is spent on hardware, not downloads.

Required

STM32CubeIDE

Eclipse-based IDE, GCC toolchain, debugger and CubeMX code generator in one installer. The ST-LINK driver ships with it — install it before plugging the board in, or Windows may bind a generic driver.

Required

STM32CubeH7 package

The HAL, LL drivers, FatFs middleware and the H7 example projects. CubeIDE downloads it on first use; grab it manually so you're not waiting on it later.

Strongly recommended

STM32CubeProgrammer

Standalone flash/erase/verify plus the ST-LINK firmware updater. When the board's ST-LINK firmware is older than the IDE expects, this is the thing that fixes it.

Recommended

MSYS2 (MinGW64) or WSL

Gives you gcc and make so the host test suite in this repo runs on Windows. WSL also makes the ST community's command-line tooling far less painful.

Recommended

A serial terminal

PuTTY or Tera Term. The ST-LINK exposes a virtual COM port on PD8/PD9 at 115200 8N1 — that's your printf lifeline all through bring-up.

Nice to have

Git + a repo

CubeIDE regenerates code on every .ioc change. Committing before each regeneration is the cheapest insurance in this whole project.

Not in the box

The Nucleo-H753ZI needs a USB Micro-B cable for its ST-LINK port and doesn't ship with one. Also confirm you have a microSD card and a way to write FAT32 to it — order both now if not.

02 / SEQUENCEThe bring-up order, and why it's this order

Each step below gives you a piece of hardware you can trust, so the next failure has only one plausible cause. Skipping ahead is how people end up debugging an SD card, an SPI bus and a clock config simultaneously.

  1. Blink LD1 on PB0

    Proves the toolchain, the ST-LINK, flashing and the debugger all work together. Set a breakpoint inside the loop and confirm it hits — you want the debugger proven before you need it.

    LED toggles at exactly 1 Hz, breakpoint halts

  2. Clock the H7 to 480 MHz and prove it

    CubeMX's clock tree view is the tool; the trap is that the H7 needs VOS0 voltage scaling and the SMPS/LDO setting to match the board before it will run at 480. Verify by toggling a GPIO in a tight loop and checking the period, or by outputting the system clock on MCO.

    Measured GPIO toggle rate matches the configured clock

  3. Get printf out over the ST-LINK VCP

    Retarget _write() to USART3 on PD8/PD9. From here on, every subsequent step can report what it's doing instead of being inferred from an LED.

    Text appears in PuTTY at 115200 8N1

  4. SPI to the ST7789 — fill the screen red

    The driver in this repo is already written and unit-tested against a mock bus; you supply five functions (write, set_dc, set_cs, set_reset, delay_ms) that call the HAL. Start SPI slow (a few MHz), then raise it once it works.

    Solid red 240×240, no border, no negative image

  5. Mount the SD card with FatFs and list files

    SPI mode first — it's slower but far simpler than SDMMC, and correctness beats throughput while you're learning. Use the TFT board's built-in slot or the separate breakout; they're the same interface.

    Filenames from a FAT32 card print over the VCP

  6. Push a sine wave to the PCM5102 over I2S

    The first sound. Generate a table in RAM, feed it out by DMA in circular mode. If it's clean, your clock tree and DMA are both right; if it's grainy or intermittent, jump straight to the cache section below.

    A steady 440 Hz tone, no clicks, no hiss

  7. Wire the encoder and drive the menu

    The decoder and menu view model in this repo are done and tested. Poll A/B from a 1 kHz timer, feed encoder_update(), push the result into ui_menu_move(). If the knob scrolls backwards, swap the A and B wires.

    One list row per physical detent, no skipping

  8. Join them: SD → ring buffer → I2S

    This is the actual DAP. The player module already encodes the preroll and refill policy; your job is the reader that fills the ring and the DMA half/full callbacks that drain it.

    A WAV file plays end to end with zero underruns

03 / PINSThe pin plan — and the two conflicts that bite

The Nucleo-H753ZI populates Ethernet and USB, so a handful of the "obvious" pins are already taken. CubeMX flags conflicts live in its pin view — treat that, plus the board's user manual (UM2407), as the final authority over any table including this one.

Conflict 1 — SPI1 MOSI

The textbook SPI1 pinout is PA5/PA6/PA7, but on this board PA7 is wired to Ethernet RMII_CRS_DV. The Arduino-header SPI1 uses PB5 for MOSI instead. Wire your display to PB5 and this is a non-event; wire it to PA7 and you'll spend an evening on a display that never responds.

Conflict 2 — the ST-LINK UART

PD8 and PD9 belong to the ST-LINK virtual COM port. Don't reassign them to something else and then wonder where your printf went. Same logic for PC13 (user button) and PB0/PE1/PB14 (the three LEDs) — free to use, but you lose the built-in indicator.

Two board-level notes worth pre-empting: PCM5102 needs its FMT/XSMT/FLT pins tied correctly or it stays muted, and the PAM8302 amp is mono — sum L and R or feed it one channel, don't tie the DAC's two outputs together.

04 / TRAPSFour H7 behaviours that will cost you a weekend

The STM32H7 is faster than the F4 everyone learns on, and most of the extra speed comes from features that are invisible until they break your audio. These four account for the overwhelming majority of "it works, but only sometimes".

1. The D-cache will corrupt your DMA buffers

The Cortex-M7 has a data cache. DMA reads and writes main memory directly and knows nothing about it. So the CPU writes samples, they sit in cache, and the DMA transmits whatever stale bytes were in RAM — intermittent noise that seems to depend on unrelated code changes.

Three ways out, in order of how much sanity they preserve: put DMA buffers in DTCM or a region marked non-cacheable via the MPU; or call SCB_CleanDCache_by_Addr() after writing a TX buffer and SCB_InvalidateDCache_by_Addr() before reading an RX buffer, with 32-byte-aligned addresses and sizes; or disable the D-cache entirely while learning and turn it on later. The last option is a legitimate choice for a first project.

Related

DMA1 and DMA2 cannot reach DTCM RAM on the H7. If your buffer is in DTCM and the transfer silently does nothing, that's why — use AXI SRAM (or SRAM1–3) with the cache handled as above, and check the linker script to see where your buffers actually landed.

2. Audio clocks are not just "divide the system clock"

44.1 kHz is not a clean fraction of 480 MHz. The H7 has dedicated PLLs (PLL2/PLL3) for exactly this — configure one to give SAI a clock that divides to 44.1 kHz family rates, and note that 44.1/88.2/176.4 and 48/96/192 generally want different PLL settings. Getting close-but-not-exact shows up as pitch drift over a long track, or a slow tick as buffers slip. CubeMX will show you the actual resulting rate; make it show you the error.

3. Preroll before you start the DMA

The single most common cause of a click at the start of every track is starting playback before the buffer is meaningfully full. The player module in this repo enforces a 75% preroll and asks for a refill below 50% — those thresholds exist so a slow SD sector never reaches the DAC as a gap.

4. Do the file I/O outside the audio interrupt

The I2S half-transfer and full-transfer callbacks run in interrupt context. Reading from an SD card there — where a single sector read can block for milliseconds — will underrun. The correct shape is: ISR consumes from the ring buffer only; main loop notices player_needs_refill() and does the reading. That split is why the ring buffer is single-producer/single-consumer and lock-free.
